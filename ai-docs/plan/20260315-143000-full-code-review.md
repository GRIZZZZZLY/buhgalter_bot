# Code Review: buhgalter_bot

**Дата:** 2026-03-15
**Scope:** Полный проект (backend Python + frontend React/TypeScript)

---

## Общая оценка проекта

**Идея:** Telegram-first персональный финансовый бот с голосовым вводом расходов, автоматическим парсингом, категоризацией и WebApp-дашбордом. Идея сильная — голосовой ввод снижает барьер для ведения учёта, а Telegram Mini App даёт нативный UX без установки отдельного приложения.

**Стек:** Python (FastAPI + python-telegram-bot + SQLAlchemy + Alembic + Whisper STT) / TypeScript (React + Vite + Recharts). Монорепо.

**Архитектура:** Чистая слоистая структура `routes -> services -> repositories -> models` на бэкенде, разумное разделение `sections/components/lib/` на фронтенде. Для MVP-стадии — хорошо. Код читаемый, файлы компактные, нет циклических зависимостей.

**Тесты:** 16 тестовых файлов покрывают основные happy-path сценарии. Для MVP — приемлемо, но edge-cases не покрыты.

## CRITICAL — Блокеры, требующие немедленного исправления

### C1. Полное отсутствие аутентификации API (Backend + Frontend)

**Backend:** `backend/app/api/deps.py` — API доверяет заголовку `X-Telegram-User-Id` без проверки. Любой HTTP-клиент может прочитать, изменить или удалить финансовые данные любого пользователя, просто подставив произвольный ID.

**Frontend:** `src/lib/api.ts:24-29` — ID пользователя захардкожен как `'555502880'`. Все пользователи WebApp отправляют запросы от имени одного человека.

**Frontend:** `src/lib/telegram.ts` — криптографически подписанный `WebApp.initData` никогда не читается и не передаётся на сервер. Используется только `initDataUnsafe`.

**Рекомендация:** Передавать `WebApp.initData` в заголовке каждого запроса, на бэкенде верифицировать HMAC-SHA256 подпись по документации Telegram.

---

### C2. Разделяемое мутабельное состояние между пользователями (Race Condition)

**Файл:** `backend/app/telegram/handlers.py:25`

```python
class TelegramTextFlow:
    _pending_category_resolutions: dict[int, PendingCategoryResolution] = {}
```

Это class variable — один словарь на все экземпляры. В async-контексте бота несколько пользователей одновременно могут перезаписывать состояние друг друга. Нет блокировок, нет TTL, нет очистки — утечка памяти при брошенных сессиях.

**Рекомендация:** Использовать `context.user_data` из python-telegram-bot, либо хранить состояние в БД.

---

### C3. Alembic миграции полностью сломаны

**Файл:** `backend/alembic/env.py:6`

```python
from app.core.settings import settings  # такого экспорта нет!
```

Модуль `settings.py` экспортирует `Settings` (класс) и `get_settings()` (функция). Переменной `settings` на уровне модуля нет. Любая команда `alembic upgrade head` упадёт с `ImportError`.

**Фикс:** `from app.core.settings import get_settings; settings = get_settings()`

---

### C4. Тихий fallback на фейковые данные скрывает ошибки (Frontend)

**Файл:** `src/lib/api.ts:93-100`

При любой ошибке API (сеть, 500, CORS, таймаут) приложение молча показывает mock-данные. Пользователь видит чужие фейковые транзакции и думает, что всё работает. Mock-данные всегда включены в production-бандл.

---

### C5. Оптимистичные обновления UI без проверки успеха API

**Файл:** `src/App.tsx:49-73`

`saveTransaction` и `deleteTransaction` применяют локальные изменения независимо от результата API-вызова. Если API вернул ошибку — пользователь видит «успех», но данные на сервере не изменились.

## MAJOR — Серьёзные проблемы, требующие внимания

### M1. WhisperModel загружается с диска на каждую транскрипцию

**Файл:** `backend/app/services/stt_service.py:100-105`

Модель Whisper (сотни МБ) создаётся заново при каждом голосовом сообщении. Загрузка занимает 5-30 секунд.

**Фикс:** Загружать модель один раз при инициализации сервиса и кэшировать.

---

### M2. `subprocess.run` без timeout

**Файл:** `backend/app/services/stt_service.py:40, 184`

Вызовы `ffmpeg` и `whisper-cpp` не имеют таймаута. Повреждённый аудиофайл может заблокировать event loop навсегда.

---

### M3. Временные аудиофайлы никогда не удаляются

**Файлы:** `backend/app/telegram/runtime.py:168-171`, `backend/app/services/audio_file_service.py:16-26`

`.ogg` и `.wav` файлы создаются в `runtime/audio/` и никогда не чистятся. Диск заполнится.

---

### M4. Репозитории коммитят по одному — нет атомарности

**Файлы:** `backend/app/repositories/transaction_repository.py`, `voice_log_repository.py`

Каждый метод вызывает `self.db.commit()`. В `voice_flow_service.confirm_voice()` цикл создаёт несколько транзакций — если процесс упадёт посередине, часть данных сохранится, часть нет.

**Рекомендация:** Unit of Work — репозитории делают `flush()`, сервис контролирует `commit()`.

---

### M5. `init_db()` конфликтует с Alembic

**Файл:** `backend/app/db/init_db.py:7-8`

`Base.metadata.create_all()` вызывается при каждом старте FastAPI. Это рассинхронизирует историю миграций Alembic.

---

### M6. Нет CORS middleware

**Файл:** `backend/app/main.py`

Telegram WebApp работает в браузере и требует CORS-заголовков. Middleware не настроен.

---

### M7. Vite proxy только для dev — production сломан

**Файл:** `vite.config.ts:9-15`

Proxy `/api-proxy` существует только в dev-сервере. В production-билде все API-запросы получат 404.

---

### M8. Нет валидации ввода в форме редактирования (Frontend)

**Файл:** `src/sections/EditSheetPreview.tsx:44-55`

Поле суммы принимает любой текст. Нет `type="number"`, нет `inputMode="decimal"`. Категория — свободный текст вместо выпадающего списка.

---

### M9. Race condition при быстром переключении периодов

**Файл:** `src/useDashboard.ts:20-38`

Cleanup-функция от `refresh()` никогда не вызывается при ручном вызове. Два параллельных fetch могут гонять.

---

### M10. Двойная инициализация Telegram WebApp

**Файл:** `src/App.tsx:18, 24-30`

`initTelegramWebApp()` вызывается дважды: в `useState` (side effects во время рендера) и в `useEffect`.

---

### M11. Нет конфигурации пула соединений БД

**Файл:** `backend/app/db/session.py:9`

Для PostgreSQL нет `pool_size`, `pool_pre_ping`, `max_overflow`.

---

### M12. SQLite timestamps без timezone

**Файлы:** `backend/app/models/transaction.py:38`, `voice_log.py:33`

`func.now()` в SQLite возвращает naive timestamp, а Python-код сравнивает с `timezone.utc`. Фильтрация по периодам может давать неверные результаты.

## Оценка архитектуры

### Сильные стороны
- Голосовой ввод — киллер-фича, снижает трение до минимума
- Чистая слоистая архитектура routes -> services -> repositories -> models
- YAML-конфигурация категорий/паттернов — легко расширять без кода
- Монорепо — единый деплой, единая версионность
- Хороший тестовый фундамент — 16 файлов тестов для MVP
- Компактный, читаемый код — файлы по 20-100 строк

### Слабые стороны
- Безопасность = 0 — нет аутентификации ни на одном уровне
- Нет DI-фреймворка — ручное создание сервисов
- Нет логирования в сервисном/репозиторном слое
- Нет rate limiting — бот уязвим к спаму голосовыми
- Нет Dockerfile — деплой не формализован
- README содержит абсолютные пути (`/home/zubr/...`)
